# 精度評価（PhiUSIIL hold-out）

## 使ったデータ

| 項目 | 内容 |
|---|---|
| データセット | PhiUSIIL Phishing URL Dataset（UCI Machine Learning Repository, CC BY 4.0） |
| 件数 | 235,795件（正規 134,850 / フィッシング 100,945） |
| ラベル規約 | **`label=1` が正規、`label=0` がフィッシング**（よくある規約と逆） |
| 使った列 | `URL` のみ。データセットが持つ派生特徴量は一切使っていない |
| 判定 | URL構造ルール（層2）のみ。既知リスト照合・コンテンツ検査は含まない |

```bash
node tools/evaluate.mjs data/PhiUSIIL_Phishing_URL_Dataset.csv \
  --url-col=URL --label-col=label --phishing-label=0 --sweep
```

## 結果

| しきい値 | precision | recall | F1 | 誤検知率 | TP | FP | FN | TN |
|---|---|---|---|---|---|---|---|---|
| 0.30 | 94.8% | 26.0% | 40.8% | 1.08% | 26,267 | 1,450 | 74,678 | 133,400 |
| 0.45 | 98.1% | 13.5% | 23.7% | 0.19% | 13,622 | 262 | 87,323 | 134,588 |
| **0.55（注意）** | **98.4%** | **10.0%** | 18.2% | **0.12%** | 10,110 | 166 | 90,835 | 134,684 |
| 0.70 | 98.7% | 5.4% | 10.3% | 0.05% | 5,495 | 70 | 95,450 | 134,780 |
| **0.85（ブロック）** | **99.9%** | **2.1%** | 4.0% | **0.0015%** | 2,074 | **2** | 98,871 | 134,848 |
| 0.90 | 100% | 1.5% | 2.9% | 0.00% | 1,477 | 0 | 99,468 | 134,850 |

判定速度は 0.18〜0.30ms/件（Node 22 / Apple Silicon）。

## 解釈

### precision は非常に高い

ブロックしきい値 0.85 での誤検知は **134,850件中2件**（0.0015%）。
しかもその2件は `www.google.blognewschannel.com` と `www.messenger.com.ge` で、
どちらも「ブランド名をサブドメイン／ドメイン名に含む別ドメイン」であり、
**検出の設計意図としてはむしろ正しい**ものです（データセット上は正規扱い）。

ブラウザ常駐で使う以上、正規サイトを止めてしまうコストは非常に高いので、
この方向の性能は実用上いちばん重要です。

### recall は低い — これは設計どおりで、同時に層構成の根拠

ブロックしきい値での recall は 2.1%。低い理由はデータの中身を見ると明快です。
このデータセットのフィッシングURLの大半は、次のような**ブランド詐称を伴わない**ものです。

```
http://www.teramill.com
http://www.f0519141.xsph.ru
http://www.shprakserf.gq
https://service-mitld.firebaseapp.com/
```

ドメイン名だけでは、無名の正規サイトと構造的に区別がつきません。
本拡張のURLルールは「**ホモグリフ・ブランド詐称・サブドメイン偽装**」という、
利用者が最も騙されやすく、かつURLに痕跡が残る型に特化しています。
それ以外の型は、URL文字列だけを見ている限り原理的に取れません。

**だから層が分かれています。**

| 型 | 担当する層 |
|---|---|
| ブランド詐称・ホモグリフ | 層2（URL構造ルール） |
| 無名ドメインの使い捨てフィッシング | 層1（既知リスト照合）— 構造に関係なく当たる |
| 正規ドメインの乗っ取り／新規ドメイン | 層4（表示コンテンツ検査）— 入力させようとした瞬間に見る |

URLルール単体の recall を無理に上げようとすると、この precision を捨てることになります。
実際、しきい値を 0.30 まで下げると recall は 26% に上がりますが、
誤検知率が 1.08%（1,450件）まで悪化します。常駐ツールとしては受け入れられません。

## この評価の限界

- **完全な hold-out ではありません。** この評価で見つかった誤検知3件をきっかけに、
  実バグを3つ修正しています（`finance`↔`binance` の一般語衝突、`e-tax.nta.go.jp` からの
  ブランド名誤抽出、`office` の汎用トークン）。修正後の FP 数値はその分だけ楽観側に寄っています。
  recall 側は、このデータに合わせた調整を一切していません。
- **データセットの正規側は素のトップページが中心**で、実際の閲覧に含まれる
  長いサブドメイン・CDN・トラッキングパラメータ付きURLが少なめです。
  実運用の誤検知率はこれより高く出る可能性があります。
- **日本語圏のフィッシング（宅配・金融・税）はほとんど含まれていません。**
  本拡張が重点的に対応している領域なので、別途 国内フィードでの評価が必要です。
- 収録されているフィッシングURLは既に停止済みのものが大半で、
  「今生きている攻撃」への当たり方を示すものではありません。

## 次に測るべきこと

1. 国内フィード（フィッシング対策協議会の事例、宅配・金融系のSMSから収集したURL）での recall
2. 実際の閲覧履歴に近い正規URL集合での誤検知率（トップページだけでなく深いURLを含む）
3. 層1（既知リスト）と層4（コンテンツ検査）を加えた状態での総合性能

# 追試: URL分類器を学習してみた結果（2026-09-20）

ルール単体の recall 2.1% を埋められないか、PhiUSIIL の正解ラベルを使って
ホスト名の文字n-gramから線形分類器を学習した。
**結論から言うと、このデータセットからは出荷できるモデルが作れなかった。**

## 何を作ったか

- 文字2〜5gramをハッシュトリックで 262,144 次元へ落とし、ロジスティック回帰
- int8量子化して約256KB。ONNXランタイムもWASMも不要で、推論は内積とsigmoidだけ
- 学習はNodeのみで完結（PyTorch不要）。教師ラベルはデータセットに付いているので蒸留ではない
- 分割は**登録ドメイン単位**。検証側のドメインは訓練に一度も出てこない

## 試した3つの変種

| 変種 | 同データ内 検証AUC | 自前コーパスでの誤検知 |
|---|---|---|
| A. ホスト名全体 | 0.941 | **20件中11件** |
| A'. ホスト名全体（`www.` 除去） | 0.926 | 20件中5件 |
| B. 登録ドメインのみ | 0.903 | 20件中6件 |
| C. 登録ドメインのみ + トップサイト15万件を正規側に追加 | **0.733** | 20件中2件 |

## 何が起きていたか

### 1. `www.` が「正規サイトの目印」になっていた

変種Aは、ドメイン単位で分割した検証で AUC 0.941 という良い数字を出した。
しかし学習に使っていない別コーパスにかけると、**`github.com`、`docs.google.com`、
`mail.google.com`、`wikipedia.org` をすべてフィッシング判定**した。

`www.amazon.co.jp` は 0.077、`mail.google.com` は 1.000。差は `www.` の有無だけ。
PhiUSIIL の正規側は `https://www.domain.tld` 形式のトップページが中心なので、
モデルは「`www.` で始まれば正規」という**データセットの癖**を学んでいた。

**ドメイン単位の分割ではこの癖を検出できない。** 癖は訓練側にも検証側にも
同じように存在するため、分割をどう工夫しても数字は良いままになる。

### 2. 正規側に有名サイトが1件も入っていない

`www.` を除去しても `google.com` や `github.com` の誤検知が残った。
PhiUSIIL の正規側は「無名だが正規のサイト」（`southbankmosaics.com`、
`uni-mainz.de`、`sfnmjournal.com` など）のクロールで、
**人が日常的に使う有名サイトが含まれていない**。
結果として「短くて有名なドメイン＝分布外＝異常」と学習していた。

### 3. 正規側を現実的にすると、性能が本来の水準まで落ちた

Tranco の上位15万ドメインを正規側に加えて学習し直すと、
自前コーパスでの誤検知は2件まで減った（しかもその2件、
`login.microsoftonline.com` と `192.168.11.1` は、実運用では
公式ドメイン／プライベートネットワークとして手前の層で打ち切られるため到達しない）。

しかし**同データ内の検証AUCは 0.903 → 0.733 へ落ちた**。
しきい値0.85での誤検知率は 3.41%。つまり、
**知らない正規ドメイン29件に1件を誤って危険と判定する。**

これが正味の実力である。最初の 0.941 は、正規側が現実の閲覧を代表していなかったことによる
見かけ上の数字だった。

## 出荷判断

**学習済みモデルは同梱しない。**

- 常駐ツールとして、知らない正規サイトの3.4%を疑うのは受け入れられない
- 重みを下げて「補助的な信号」に留める案もあるが、
  `mail.google.com` に 1.000 を返すような信号は、重みを下げても測っているものが違う

一方で、次のものはリポジトリに残した。再挑戦の足場になるため。

| 残したもの | 用途 |
|---|---|
| `extension/src/core/url-classifier.js` | 推論（外部依存ゼロ）。モデルを置けば動く |
| `tools/train/train-url-classifier.mjs` | 学習。`--scope` と `--benign-list` を切り替えられる |
| `tools/train/validate-url-classifier.mjs` | **別コーパスでの出荷判定**。誤検知が1件でもあれば exit 1 |

## この経験からの教訓

**同じデータセットを分割しただけの検証は、出荷判断に使えない。**
ドメイン単位の分割という「正しい」分け方をしてもなお、データセット固有の癖は
両側に残り、数字を持ち上げる。

出荷可否は、**学習に使っていない別の分布**で判断する必要がある。
`validate-url-classifier.mjs` を独立したスクリプトとして置いているのはそのためで、
これが通らない限りモデルは同梱しない。

## 次にやるなら

1. **正規側を実際の閲覧履歴に近づける**。トップサイトリストだけでなく、
   深いパスを持つURLや、CDN・業務システムなどの「普通だが無名」なドメインを含める
2. **国内フィードで評価する**。PhiUSIIL には日本語圏のフィッシングがほとんど含まれていない
3. **層全体で測る**。知りたいのは分類器単体の精度ではなく、
   「ルールが取りこぼしていたものを、誤検知を増やさずに拾えるか」
